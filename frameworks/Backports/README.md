# Backports

Lists every iOS SDK member that exists on iOS, emits a skeleton with a stub for each one `src/` does not implement (a stub is used only where the system lacks the member), and counts how many are implemented and how many are unavailable on iOS.

## Scope

Every member of every iOS SDK framework is a candidate, and the generator applies one rule to decide whether it gets a stub: the member exists on iOS. A member is left out, counted as `unavailable on iOS` and never stubbed, when the header marks it unavailable on iOS (`API_UNAVAILABLE(ios)`), when its class is unavailable on iOS, or when its introduction is before the first iPhone OS release (2.0). No target release appears in the generator, its facts or its names. Whether the system's member or the one in the library is used is decided on the device, at load or at first call, the same way on every release.

## Facts

- ObjC and C: the umbrella header is run through `clang -Xclang -ast-dump` as text and streamed. `AvailabilityAttr` gives the introduction. A redeclaration prints a `prev <address>` pair before the name; the parser drops it, so a class, protocol or function is never named `prev`. Each row has a `flags` column of space-separated words: `unavailable` for a class, method or property that the header marks unavailable on iOS (`API_UNAVAILABLE(ios)`, `NS_UNAVAILABLE`, or `__attribute__((unavailable))`), `nonruntime` for a protocol marked `objc_non_runtime_protocol`, and for a property `class` (a class property) and `getter:<selector>` (a custom getter, as in `getter=isEnabled`). An unavailable row gets no stub: no app built against the iOS SDK can reference it. When two declarations of one member disagree, the member is unavailable if either says so, and the protocol flags carry `unavailable` as well.
- Swift: `swift-api-digester -dump-sdk -swift-only` writes JSON, with one module cache shared by all frameworks.
- Each framework is one TSV in `build/generated/backports/cache/<sdk version>-<generator digest>/`. Four shards run in parallel under `/bin/sh`.

## Skeleton

`build/generated/backports/skeleton/` holds `revenant_backports.h`, `registrar.m`, and per framework one `<N>.m`. C functions are compiled as Objective-C with the rest of the framework, because their parameter types come from the umbrella header; there is no `<N>.c`.

- Each member that exists on iOS gets a stub that aborts with its name, for example `not implemented: -[NSUUID UUIDString]`. The skeleton does not read `src/` for members: a stub is inert wherever `src/` implements its member.
- Classes: each class that exists on iOS and that `src/` does not implement gets `REVENANT_ALIAS_OF(X, Super)` in its framework's `<N>.m`, so `_OBJC_CLASS_$_X` and `_OBJC_METACLASS_$_X` are aliases of `RevenantX` (`revenant_alias.h`). The proxy forwards to the system's `X` when there is one. `src/` is read once, with `grep`, for the names it implements: `@implementation X`, `REVENANT_ALIAS(X)` and `REVENANT_ALIAS_OF(X, ...)`, and any name passed first to an upper-case macro (a macro such as `REVENANT_AX_MATH_EXPRESSIONS_ONLY(X)` can expand to `@implementation X`). A class is then never defined twice in a library. The macro rule can also skip a name that is only passed to a macro; that class then has no proxy, and `status.txt` shows it as not reachable. A class unavailable on iOS gets no proxy, and a proxy whose superclass is unavailable on iOS inherits from `NSObject`.
- ObjC methods and properties are added by `revenant_backports_register` with `class_addMethod`, only when the class does not already respond to the selector, so the system's implementation wins, as in `attach.c`. The class is `X` when the runtime has it, otherwise `RevenantX`. No class is created at run time.
- Protocols: each protocol that exists on iOS and is not marked `objc_non_runtime_protocol` is referenced with `@protocol` from the constructor, so the image registers it and `NSProtocolFromString` finds it. Clang gives every image a private copy of a header protocol (`weak private external`), so an app links an absent protocol without any library export.
- Global variables: a weak definition `__typeof_unqual__(revenant_type_X) revenant_global_X __asm__("_X") = {0};`, after `typedef TYPE revenant_type_X;`. `TYPE` is the type text the facts carry, without the `extern` and the `*_EXTERN` and `*_EXPORT` macros that some headers put in front of it (`MTL_EXTERN NSErrorDomain`), which a `typedef` refuses; it is not `__typeof__(X)`, which fails on a symbol the header marks unavailable. The unqualified type removes a top-level `const` however it is spelled, including one hidden behind a typedef such as `PDFAnnotationKey` (`NSString *const`): a const definition would sit in `__TEXT,__const`, and the load constructor would write into read-only memory and die with a bus error before `main`. At load, `revenant_backports_global` copies the value of the system's `X` into the storage when the image that exports `X` has it (`dlopen` of that image, then `dlsym`). When the system has no `X`, an Objective-C global keeps a missing-value object that aborts on use, and a scalar stays zero. A global array has no size the copy can use, so it is not copied; `status` counts it as `not copied`.
- C functions: a typed forwarder with the signature's parameter types, `RET revenant_c_N(params) __asm__("_X")`. Its first call resolves `X` with `revenant_backports_c_target`, in the image that exports it: the install name of the `.tbd` that lists `X`, or the framework binary of its header when no `.tbd` lists it. When the system has `X`, the forwarder tail-calls it with the same arguments, so the system's definition is used on every release. When the system does not, the forwarder aborts naming the member, as a stub does. A variadic function, or a signature the generator cannot split into a return type and parameter types, gets no stub: the count `not stubbed` names it, and an app that calls it fails to link.
- Swift function stubs are weak definitions bound to the mangled symbol, so the strong definition in `src/` wins at link time within a library. They have no forwarder yet (see Limits).
- A C function or global that `src/` implements is compiled from `src/`: its strong definition wins at link time, so the system's member is not used there (see Limits).

## Implemented count

The implemented members are the symbols of the objects that `src/<Framework>` compiles to, read from `build/.objs` with `nm` (classes, C functions, global variables) and the same `nm` listing for methods (with their class or category and selector). A property counts when its getter is implemented: the getter is the custom selector when the header gives one (`getter=isEnabled`), and a class property's getter is a class method. A method of a `Revenant<Name>` proxy counts for `Name` when `src/` implements it on the proxy. `-init` counts as implemented, because a class that does not implement it inherits `NSObject`'s, which every proxy inherits too. The clang AST was the first source of these keys; reading it cost hours on each cold build.

- Swift: a `$s` symbol that the objects define (any letter but `U`) implements the Swift member with that mangled symbol. The Backports libraries are armv7 and compile only `.m`, `.mm` and `.c`, so no Swift object is built today and the Swift count reads zero. The stock Swift compiler refuses an iOS 6 deployment target (its minimum is iOS 7.0), so an armv7 Swift build needs the revenant `swift` package, which this job does not build. `frameworks/SwiftUI` and `frameworks/Combine` are separate components: the Backports job builds neither, so their symbols are not counted.
- Protocols: a protocol counts as implemented when a source under `src/` defines it, meaning a `@protocol Name` line with no `;` after the name (a forward declaration or a `@protocol(Name)` expression does not count). The rule reads the sources, not the objects: clang gives every image a private copy of each protocol a translation unit references, so an object cannot tell a definition from a use.
- Reachable: a member is reachable when a library exports its symbol (a class's `_OBJC_CLASS_$_`, a C function, a global, a Swift stub), or when a library's ObjC metadata has the method (a proxy's methods count for its class). A property counts when its getter is reachable. Protocols are not counted in reachable: the libraries register them by name, which the export check cannot see.

## Commands

- `./xmakew l -P . frameworks/Backports/tools/generate.lua`: the facts (cached per SDK and generator digest) and the skeleton of every framework. The configure of the component runs it once, in a fresh process; its last line counts the members that exist on iOS and are not stubbed (`unavailable on iOS`), the globals not copied and the C functions not stubbed.
- `./xmakew l -P . frameworks/Backports/tools/exports.lua [libdir] [report]`: after a build, reads the objects in `build/.objs` and the dylibs in `build/iphoneos/armv7/release` once each, checks every key of the objects against them, and writes `exports.txt` (per kind: implemented, exported once, missing, duplicated, not public; then the missing, duplicated and not public lines) and `status.txt` (`implemented X of Y, reachable Z of W` per framework: implemented counts what `src/` defines, reachable what some library exports; the total line sums both) beside `report`. It fails when a public symbol or method is missing, or when two libraries export the same class, function, global or method.
- `./xmakew l -P . frameworks/Backports/tests/backports_test.lua`: fixture test.
- `./xmakew build -P . BackportsProbe` then `./xmakew l -P . frameworks/Backports/tools/probe.lua build/iphoneos/armv7/release/BackportsProbe`: links `tests/probe/probe.m` for armv7 against the libraries. The probe uses an absent class and its class method, an absent protocol, and an absent C global, all through the 26.2 headers, and does not link HealthKit. The checker prints `otool -L` and fails unless every load command is a Backports library or a library or framework iOS 6 has.
- `./xmakew f -P . -p iphoneos -a armv7 --component=Backports` then `./xmakew build -P . FoundationBackports`: one shared library per library of the former package, `lib<Name>.dylib` with its install name under `/usr/lib/revenant/org.revenant.backports`. Each compiles `src/<Framework>`, `src/attach.c` and the skeleton of its framework, which configure generates; the build's deployment target is the only minimum, with no bands, and the generator reads none. The component option configures only this component and what it needs, and the build reads the iOS 26.2 SDK, so the sources compile against the headers they are written for.
- `REVENANT_GEN_SDK=<iPhoneOS SDK folder>` overrides the SDK the toolchain resolves.

## Public symbols

A key is public when the SDK both declares it and exports it: a class, C function, global or method declared in a framework's headers (from the clang AST, as the facts are), and for classes, functions and globals, also exported by a framework's `.tbd` (`tools/public.lua` scans each framework's `.tbd` for the names the headers declare). Methods are public through the headers alone. A key that is not public is counted and does not fail the check, and each class that is not public is listed.

`__NSConcreteUUID` is the one class the report lists as not public among the Foundation keys of the objects. The iOS 26.2 SDK's `Foundation.tbd` exports `_OBJC_CLASS_$___NSConcreteUUID`, but no Foundation header declares it, so it is not a declared symbol. The iOS 6.1.3 shared cache (read with `toolchain/modules/apple/dyld.lua`, `exported_by`) does not export it from Foundation, while it exports `NSUUID` and `NSTimer`; the class exists there only in Objective-C metadata, as a private class. An iOS 6 target never exported it, so the backport owes no export for it.

Methods of a `Revenant<Name>` proxy count as methods of `Name` when the library also exports `_OBJC_CLASS_$_<Name>`: the alias makes the proxy the class at run time (`revenant_alias.h`).

`NSUUID`, `NSProgress` and `NSJSONSerialization` are not defined twice. Each publishes through `revenant_alias.h`, so the system class answers wherever it exists, and their methods are category methods that the loader adds only where the system lacks the selector. An option bit is a capability rather than a version, so `NSJSONSerialization.m` probes the system method for each bit it may need to wrap, once, in a constructor, before any wrapper is installed: unescaped slashes (`{"a/b":1}` must come back without `\/`), sorted keys (sixteen keys must come back in byte order), JSON5 reading (`{a:1}` must parse) and top-level dictionary reading (`"a":1` must parse as a dictionary). A probe that fails installs the wrapper for that bit only, and the wrapper hands every other option to the system method. A probe answers yes when the system method is absent, because the category method is then the implementation.

Methods are read from the libraries with `toolchain/modules/apple/objc.lua` (`binary_inventory`), which folds categories into their class, and from the objects with `nm`, which lists each method implementation as `-[Class sel]` or `+[Class sel]`. The objects are read once, in batches, for both reports.

## Limits

Swift types, variables and protocols are counted but not stubbed. The skeleton emits no protocol objects: a protocol that `src/` defines is registered at load only when its file uses it, because clang emits a protocol's metadata only in a translation unit that references it. So each such file ends with `revenantEmitProtocols`, which takes `@protocol` of every protocol the file defines (`UIKit/QuartzCoreProtocols10.m`, `HomeKit/HMHomeDelegateProtocols8_0.m`, `Foundation/NSURLSessionStreamTask9.m`). The object files carry the metadata and `tests/QuartzCore/protocols_test.m` checks it on the host; it has not been run on a device. `_OBJC_CLASS_$_` class symbols are not emitted either, so an app that links an absent class does not link yet. Subframeworks and enum constants are excluded. ObjC type encodings are empty.

The shadowing gaps are these, and none is measured on a device. A C function or global that `src/` implements is linked from `src/`, so on iOS 7 and later the system's member is not used there: moving `src/`'s definition under another name needs an object-level rename, which is not built. The generator does not stub such a member: `implemented_names` reads the function and constant definitions in `src/` by text, and skips the stub for each one it finds (612 C functions in the 26.2 SDK, counted as `implemented in src`). The text scan misses definitions that a macro generates, that begin with `__attribute__`, or that declare a global without `const`; for those the stub stays, and the library links `src/`'s definition (the strong one), so the stub is dead there. The build measures 46 such stubs across the libraries, and no two libraries export one symbol (the export check, `duplicated 0`). A global is copied once, when the library loads, so a system value that changes later is not seen. A Swift function stub is linked with the library and has no forwarder, so on iOS 7 and later it shadows the system's Swift symbol. A variadic C function is not stubbed (the 26.2 SDK declares 12 of them that exist on iOS, and the count `not stubbed` names them), so an app that calls one fails to link. A Swift member that is unavailable on iOS is not detected either: the digester's JSON carries `intro_iOS` and `declAttributes` but no iOS-unavailable marker, so the Swift stubs cover every Swift symbol the SDK declares, including any that iOS does not have.

Partly backported. Each of these builds, and the part it does not cover is missing from the module, so a program that uses it fails to compile against the backport rather than running with a fake:

- `Network` (`swiftNetwork`, wrapper `revenant@network`): `NWConnection` over TCP and UDP POSIX sockets on the queue it starts on, `NWPathMonitor` over `SCNetworkReachability`, and `NWEndpoint` with the address types. A refused TCP connect goes to `waiting`, as on iOS. `NWListener` accepts over BSD sockets and a dispatch source, and `NWProtocolTCP.Options` maps to `setsockopt`. `NWParameters` is a class, as on iOS, so a connection or listener holds the object its caller passed and sees later changes to `preferNoProxies` and `allowLocalEndpointReuse`. `NWParameters(tls:tcp:)` takes the TLS and TCP options with the SDK's defaults, so `NWParameters(tls: nil)` is plain TCP; a non-nil TLS option is applied to each connection, and a listener, or an accepted connection, whose TLS options have no server identity fails with `ENOTSUP`. A framer (`NWProtocolFramer`, `NWProtocolFramerImplementation`) frames the byte stream of one connection. `NWConnection.receiveMessage` returns one message at a time: a framed message carries the framer's `label` as its content context identifier and is complete, and a datagram carries `socket`, as macOS reports them in `tests/Network/main.swift`. The host test does not compare an unframed stream message, so that path is not verified against macOS. `ContentContext.isFinal` is set on the TCP receive context, as the SDK header describes; a sending context marked final does not write-close the socket yet, and neither does `isComplete` on plain TCP. `viabilityUpdateHandler` reports `true` when the connection becomes ready and `false` when a viable connection goes to `waiting` or `failed`; it follows the state rather than the path, so a route change under a ready connection is not reported, and cancelling does not report, as on iOS. `import Network` re-exports `RevenantNetworkC`, a clang module that declares the `nw_*` C API which Telegram's `RustStreamHost.swift` calls (`nw_connection_t`, `nw_error_t`, `nw_connection_state_t`, and the functions and `_nw_content_context_default_message` it uses), transcribed from the SDK's Network headers. Its `sec_protocol_options_*` declarations come from the SDK's `Security/SecProtocolOptions.h`, which it includes. Its module map and header are installed beside `Network.swiftmodule` in `lib/swift/iphoneos`, the directory a consumer passes with `-I`. The functions are implemented in `libNetworkBackports` (`sec_protocol_options_*` in `libSecurityBackports`), and `_nw_content_context_default_message` is defined in `nw-default-context.c`. The module does not re-export the SDK's Network module, so a consumer's `llvm.linker.options` has no `-framework Network`, which iOS 6 does not have. Other parts of the C API are not declared. Missing: TLS itself, the UDP option type, `NWBrowser` and the rest of the framework. `NWInterface.type` reads the interface name (`en` wifi, `pdp_ip` cellular, `lo` loopback), so it is an approximation. `NWPathMonitor` builds each `NWPath` from `SCNetworkReachability` (status, expensive on `isWWAN`), `getifaddrs` (interfaces), the `sysctl` `NET_RT_DUMP` route messages (gateways, and the interfaces that carry the default route), and `res_9_ninit` from `libresolv` (`supportsDNS` is `nscount > 0`; iOS has no `/etc/resolv.conf`, and the resolver reads the configuration configd publishes through dnsinfo). Updates arrive on the queue `start(queue:)` names, and `cancel()` stops them; `queue`, `currentPath` and `AsyncSequence` updates are there too, and required and prohibited interface types filter the path. Against macOS it differs in three places: `bridge` interfaces appear only on macOS, the interface list has one duplicate entry whose cause is not yet known, and the prohibited-interface list semantics differ. `RadioType` (iOS 15) and `ethernetChannel` (macOS only) are not implemented. `tests/network_test.lua` compares the connection, path and endpoint results with the host on the same socket exchanges. `tests/network_cseam_test.lua` compiles the C calls of Telegram's `RustStreamHost` against the SDK's Network module and, through `import Network`, against the backport, and checks that the backport's consumer has no `Network` framework link; it compiles the calls and does not run them. The overlay no longer uses the `nw_*` C seam, so the iOS 12 gate is gone.
  The ciphersuite groups (`tls_ciphersuite_group_t`) expand to the lists in `protocol/SecProtocolHelper.m` and `protocol/SecProtocolInternal.h` of `apple-oss-distributions/Security`, read as facts into `NWProtocolTLS.swift`; the static PSK suites are never added, only `ECDHE-PSK-*`.
  The C API TLS (`nw_connection.m`) is one SecureTransport path capped at TLS 1.2: it refuses verify and challenge blocks, client identities, PSK, OCSP, SCT, ciphersuites and ALPN with the matching OSStatus and a stderr line.
  Measured on an iPhone4,1 running iOS 6.1.3 with `emulator/tests/guest/connect/tls.swift`, which handshakes to ten hosts with TLS 1.2 and 1.3 maximums, prints the version and cipher suite each one negotiated, and compares with `NSURLConnection`. ## Compile-only declarations

`Translation` (`swiftTranslation`, wrapper `revenant@translation`) is the one entry that cannot be implemented, so it is not an open gap: the gap rule above would refuse it. The framework asks the system for its translation service, and iOS 6 has no translation service and no language models to ask. The module declares the SDK's public surface and behaves as a system without a service: `LanguageAvailability` reports no supported language and the `unsupported` status, `TranslationSession` throws `TranslationError.unsupportedLanguagePairing` (`nothingToTranslate` for an empty text) from `translate`, `translations(from:)` and `prepareTranslation`, `translationTask(_:action:)` and `translationTask(source:target:action:)` run their action with a session whenever the configuration is set, and `translationPresentation(isPresented:text:attachmentAnchor:arrowEdge:replacementAction:)` presents nothing: when `isPresented` is true it writes one line to stderr and the system log, sets the binding to false as a dismissed presentation does, and never calls `replacementAction`, because no translation was produced. Every declaration carries the SDK's availability (iOS 18.0 for the framework and `translationTask`, iOS 17.4 for `translationPresentation`), so a use guarded by `#available` typechecks and builds for armv7, and on iOS 6 the guard is false: Telegram's Translate action and its translation view, which call the members only under it, are not offered. The SDK ships `Translation` for arm64e only, and the cross-import overlay that declares the View members (`_Translation_SwiftUI`) is arm64e only as well, so an armv7 build has them only when this module is on its Swift search path. `tests/translation_test.lua` compares the public surface of `TranslationSession.swift` with the SDK's `Translation` interface, requires the shim's `translationPresentation` and both `translationTask` overloads to take the SDK's parameter lists, with the same defaults, for the same availability, compiles the shim for armv7, typechecks calls built from the SDK's parameters and a use shaped like Telegram's translation view, and checks that unguarded uses fail with the availability error.

## Lowering gaps

These demand-map references are SDK declarations whose availability lowering belongs to `toolchain/modules/apple/lowered.lua`:

- `Accelerate.kvImage420Yp8_Cb8_Cr8` and `Accelerate.kvImageARGB8888` are enum values used by TelegramVoip's `OngoingCallContext.swift`.
- `Foundation.PresentationIntent` is the Swift overlay type used by BrowserUI's `BrowserMarkdown.swift`; the Objective-C `NSPresentationIntent` implementation is already in `src/Foundation/NSPresentationIntent15.m`.

The Swift overlays below are built as targets of this component, and each builds only for an iOS its backport reaches. Below that release the build refuses, and the wrapper package refuses on load, with "not yet backported". None of these is a supported minimum: each closes when its backport makes it build at iOS 6.

- `swiftRealityFoundation` and `swiftRealityKit` below iOS 8: they load SceneKit, and the SceneKit members they import (`SCNHitTestResult`, `-[SCNView hitTest:options:]`, `+[SCNNode nodeWithGeometry:]`) are not backported yet. RealityKit's UIKit part is open too. [RealityFoundation below iOS 8](../../docs/reference/backports/RealityFoundation/SceneKit.md) says what brings them back.
- `MusicKit` (wrapper `revenant@musickit`): `src/MusicKit/Catalog.swift` uses `URLQueryItem` with `queryItems`, which needs iOS 8. Its `URLComponents` use no longer needs iOS 7: the class lost its guard, and its alias exports it, so the reference binds to the Backports image. Its build refuses with "not yet backported" before it compiles.
- `SwiftData` (wrapper `revenant@swift-data`): `src/SwiftData/DefaultStore.swift` imports `FoundationEssentials`, which the iOS 6 SDK does not provide ("no such module 'FoundationEssentials'"). Its build refuses with "not yet backported" before it compiles.

None of these is built or required by the swift job, and their wrappers refuse on load with the same message.
