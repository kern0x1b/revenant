# Core ML, the model-update classes

What `packages/frameworks/apple-backports/CoreML/CoreMLUpdate13.m` and `CoreMLUpdate14.m` carry, what the host does with
the same model, what was measured, and what was not.

## WHAT THE OBJECTS HOLD

| class or method | status | what it answers |
| --- | --- | --- |
| MLTask | implemented | taskIdentifier, state, error; -resume and -cancel move the state as MLTask.h:41-45 gives them |
| MLUpdateTask | implemented | the four constructors; the training that -resume starts; -resumeWithParameters: |
| MLUpdateContext | implemented | the five readonly properties; built by the training loop, not by callers |
| MLUpdateProgressHandlers | implemented | -initForEvents:progressHandler:completionHandler: holds both blocks; the loop calls them |
| MLWritable | owed | the protocol is not declared by any header of this port; the adopter exists (below) |

The four constructors (MLUpdateTask.h:23, :30, :36, :43):

- `+updateTaskForModelAtURL:trainingData:configuration:completionHandler:error:` (:23) - iOS 13, the class's own
  availability; CoreMLUpdate13.m.
- `+updateTaskForModelAtURL:trainingData:completionHandler:error:` (:30) - iOS 14 (`API_AVAILABLE(ios(14.0))`);
  CoreMLUpdate14.m forwards it to :23 with a nil configuration.
- `+updateTaskForModelAtURL:trainingData:configuration:progressHandlers:error:` (:36) - iOS 13; CoreMLUpdate13.m.
- `+updateTaskForModelAtURL:trainingData:progressHandlers:error:` (:43) - iOS 14; CoreMLUpdate14.m forwards it to :36
  with a nil configuration.

**Availability correction.** The earlier registry rows and the comment in CoreMLUpdate13.m said both initialisers
are iOS 14. That was wrong: the two with a configuration carry no annotation of their own, so they inherit the
class's `ios(13.0)` (MLUpdateTask.h:19), and so does -resumeWithParameters: (:50). Only the two without a
configuration are `API_AVAILABLE(macos(11.0), ios(14.0))`. The registry now has a row for each of the five
methods, in ios13.json or ios14.json.

**Not used.** The configuration is accepted and ignored: the port trains on the CPU, which is what the host's
test runs on. -resumeWithParameters: refuses a non-empty dictionary by name, because the values are not applied.

## THE LIFECYCLE

`revenant_ml_taskForModelAtURL:` (CoreMLUpdate13.m) reads the model file, makes the trainer, takes the samples from
the batch provider, and returns a task in state 1 (Suspended). `-resume` (the override in MLUpdateTask) moves the
task to Running and starts the loop on the task's serial queue. The loop:

1. delivers `TrainingBegin` (metrics empty);
2. for each epoch, for each mini-batch: checks for cancellation, runs one trainer step, delivers `MiniBatchEnd`
   with `miniBatchIndex` (and no `epochIndex`);
3. delivers `EpochEnd` with `epochIndex` (and no mini-batch index);
4. writes the snapshot: the trainer's weights are stored into the model, written with `-writeToURL:error:`
   to a temporary `.mlmodel`, and read back as the context's model;
5. sets state 4 (Completed) and calls the completion handler once, with event 0 and empty metrics.

A trainer error sets state 5 (Failed) with the trainer's message and stops the loop. A progress handler is called
only for the events its mask asks for. Every context's model is a `RevenantMLWritableWrappedModel`, which adopts
`MLWritable` (the snapshot is written through it).

**The host's behaviour, measured with the same model** (`tests/backports/host/coreml-update/host-train.m`):
the mini-batch index restarts at 0 in each epoch; mini-batch-end events carry no epoch index; epoch-end carries
the epoch index only; the completion event is 0; the states are 1 then 4. The host also reports a loss at
mini-batch and epoch-end events. The port reports none (see THE LOSS).

## THE MEASUREMENTS, AND THE COMMANDS A READER CAN RUN

Everything below runs with `sh tests/backports/host/coreml-update/run.sh`. The model is generated by `gen.c`
(16 samples, mini-batches of 4, 2 epochs, seed 7) and trained three ways: by the host's MLUpdateTask, by the port's
trainer (`train-check.c`), and by the port's MLUpdateTask built for the Mac (`port-train.m`, linked against the port's
own sources, not the host's framework).

**Weights, against the host.** The bound is 4 float32 ulps of the largest weight in the host's dump of the event
(`compare.awk`). Worst over the 12 events of each case (training begin, 8 mini-batch ends, 2 epoch ends, final):

| case | trainer against the host | port's MLUpdateTask against the host |
| --- | --- | --- |
| SGD, no momentum (learning rate 0.1) | 1.01 ulp | 1.01 ulp |
| SGD, momentum 0.9 (learning rate 0.1) | 1.01 ulp | 1.01 ulp |
| Adam (learning rate 0.01, beta1 0.9, beta2 0.999, eps 1e-8) | 2.01 ulp | 2.01 ulp |

**Events.** For all three cases the port's sequence of events (order, step names, epoch and mini-batch indices,
completion, states) is identical to the host's (`run.sh` compares them with the loss removed).

**Snapshots.** The host's dumps are written by `host-train.m` from the model the host hands back in each context.
The port's snapshots are written with `writeToURL:error:` and read by `dump.c`. The flatten layer has no weights,
and `run.sh` leaves it out of the port's dump so the two listings line up.

**Oversized models.** `gen.c` takes an optional convolution output-channel count. `run.sh` builds a model with
2^31 - 1 output channels and one with 2^27. The trainer refuses both before it allocates, with a line naming the
convolution: 2^31 - 1 fails the check on the dimension ("the convolution's shape is not one the trainer runs"),
and 2^27 fails the check on the weight count, 2^27 * 9 values, which is beyond the 2^28 limit ("the convolution is
too large for the trainer").

**Adam, and why the worst value is 2.01 ulp.** The first Adam differential was 5e-7 off. The cause was in the
constants: beta2 was computed in float32, and 1 - 0.999 in float32 is 0.00099998713 instead of 0.001, a relative
error of about 1.3e-5 in the second-moment decay. The update now computes in double precision with beta1 and beta2
as double constants, and the step count is incremented before the update, so the bias corrections use the step
of the mini-batch. What remains is float32 rounding: the velocity and the second moment are stored as float32, and
the value is stored as float32 after the update, which is a few roundings per weight per step. Those account for
the worst measured value, 2.01 ulp, which is inside the 4-ulp bound. The bound is not widened for it.

## THE LOSS: NOT IDENTIFIED

The host reports a loss at each mini-batch and epoch end. The port reports none, and the events are compared
without it. What was measured (scratch in `.agent-work/runs/update/loss/`):

- **Scale (probe a).** With the weights fixed, the reported loss scales linearly with the residual: scaling the
  error (y - t) by k = 1, 2 and 4 scales the loss by k. It is zero at zero residual and it takes negative values.
  So it is not a squared error.
- **Index shift (probe b).** Each reported loss was compared with the mean squared error of the previous and the
  next mini-batch. No shift matches.
- **Wiring (probe c).** The loss layer's inputs were checked against the model file: the residual is the
  network's output minus the target input `t`. The wiring is as the model describes it.
- **Fit across all samples, then holdout.** The per-sample coefficient c_s = dL/dy is not an affine or quadratic
  function of (y, t) on the held-out samples. It is approximately affine in the 36 inputs (holdout RMS 0.007,
  against a coefficient scale of 0.08), but not exactly.
- **Ruled out:** the mean and sum of squares, a half factor, a delta between samples, a running mean, a signed
  sum, and an index-shifted MSE.

So the loss is not yet a function the port has identified. The events are compared without it, which is the only
claim this page makes about it.

## WHAT WAS NOT MEASURED, STATED PLAINLY

- **Cancellation.** The loop checks for it before each mini-batch and leaves the state at Cancelling without
  calling the completion handler. No host case drives it.
- **Failure.** A trainer error sets state 5 with the message and stops. No host case drives it.
- **Completion-only constructors.** The two constructors without progress handlers (:23 and :30) are not driven
  by any host case. The harness drives :36 only.
- **-resumeWithParameters: with values.** Refused by name; not compared with the host.
- **MLUpdateContext.parameters and the metrics at training begin and completion.** The port gives empty
  dictionaries; the host's contents were not inspected.
- **The host's snapshot format.** The host writes a compiled package; the port writes a `.mlmodel`. They are
  compared by the reader's dump, not by bytes.
- **Feature names.** The port hard-codes `x` and `t`. A model with other names is not handled.
- **Field width.** `revenant_ml_int` truncates a model field above 2^31 before its range check; such a model is
  refused later, by the count mismatch.
- **Device.** No device run was made; the training runs on the CPU in the port.
